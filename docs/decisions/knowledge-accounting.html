knowledge accounting is a declaration, not a diff

A plan accounts for its knowledge by declaring paths that must exist, not by proving the files changed on its branch.

decision tech debt cleared knowledge declaration gate
Current as of 2026-07-25

The decision

A plan accounts for the knowledge it produced by naming it in a knowledge: field. The guard checks two things and nothing more: every named entry is a concepts/, decisions/, or specs/ file, and every named file exists under docs/.

The guard does not consult git. It does not ask whether the named document was created or modified during this plan's work, and it does not require any file under the knowledge directories to appear in the branch's diff.

Work that produced no knowledge uses an explicit escape hatch with a written justification:

knowledge: none
knowledge_reason: dependency version bump only, no behavior or pattern changed

none on its own is refused. The reason is mandatory, in the same way an abandoned plan must record why it was dropped.

What this rules out

The rejected alternative was proof by diff: compare the branch against main and require that at least one file under docs/concepts, docs/decisions, or docs/specs actually changed. That is a stronger claim — a declaration can point at a document written months ago and satisfy the check, while a diff cannot be fooled that way.

It was rejected because the extra strength is narrow and the cost is broad. A diff check needs a merge base, which means it needs to know the trunk's name, that the trunk exists locally, that the branch is not detached, and that git can answer at all. Every one of those is an environment in which the check either fails open or refuses honest work for reasons that have nothing to do with knowledge. The existing rules only ever ask git for the current branch name, and they treat a silent git as "not a repo" rather than as an error. Making the knowledge gate the first rule with a hard dependency on repository topology would be the most fragile thing in the engine.

The narrower point: the gate's job is to make skipping the knowledge base impossible to do silently, not to be unfoolable. An agent that points knowledge: at an unrelated old document has written a false statement into a file that locks forever and sits on the hub page under the plan's name. That is a visible lie, which is the level of accountability this harness is built on everywhere else — the commit hook cannot tell whether a commit message is true either.

What follows from it

Documents are written before the plan resolves, never after, because the path has to exist for the flip to be allowed. The ordering is deliberate: the knowledge lands while the work is still fresh.

Because the check is shallow, the instructions carry the weight. .harness/instructions/knowledge.md defines when a concept, a decision, or a spec is owed, and .harness/rules/RULES.md — injected into every session — carries the rule itself. Weakening those documents weakens the gate far more than any change to the guard would.

Updating an existing document counts as knowledge, and is listed the same way. That falls out of the design rather than being a special case, and it is the correct behavior: work that changed how a documented thing behaves owes a rewrite of that document, not a new one.
