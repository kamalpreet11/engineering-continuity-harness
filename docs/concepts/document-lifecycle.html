document lifecycle

How a plan and a decision reach their final state, and what the harness demands at that moment.

concept lifecycle resolution lock knowledge
Current as of 2026-07-25

Two kinds of harness document have a life that ends: a plan, and a decision. Everything else in docs/ is simply kept current. This concept covers how those two reach their end, and why the ending is the place the harness asks for something.

A plan's states

A plan's state: is one of four values, and only the first is editable.

StateMeaning
createdLive work. The plan can be edited freely.
implementedThe work is done and verified. Locked.
abandonedThe work was dropped. Locked.
supersededA newer plan replaced it. Locked.

The three ending states are collectively a resolution. Reaching one is a one-way door: the guard refuses every later edit to that file, so a plan is a record of intent that cannot be quietly rewritten after the fact.

Why the resolution edit is the enforcement point

Because the file locks the instant its state stops being created, the edit that resolves a plan is the last edit it will ever receive. Anything the resolution requires has to arrive in that same edit — there is no second chance to add a missing date afterwards.

That makes it the one moment every piece of work must pass through, which is why the harness collects its dues there:

Resolving toThe edit must carry
implementedimplemented: date, and a knowledge: accounting
abandonedabandoned: date and abandoned_reason:
supersededsuperseded: date and superseded_by:

The knowledge accounting

A plan cannot claim to be implemented without saying what the work taught the project. Its knowledge: field names the concepts, decisions, and specs the work produced, as paths under docs/ separated by |:

knowledge: concepts/auth-flow.html | decisions/token-storage.html

Every named file must exist, so the document is written before the plan can close. Work that genuinely produced no knowledge says so and says why:

knowledge: none
knowledge_reason: dependency version bump only, no behavior or pattern changed

The check is deliberately shallow: it confirms the plan accounted for its knowledge and that the files are real. It cannot judge whether a document is any good, and it does not try. It is a forcing function, not a reviewer — the judgement of what counts as a concept, a decision, or a spec belongs to the agent, and the instructions carry it.

A decision's ending

A decision has no state field. It ends when a newer decision replaces it: the new file names the old one in supersedes:, and from that moment the old file is read-only.

The lock reads the replacement, not the original, because a superseded decision stays exactly as it was written — nothing edits it to mark it dead. So the guard looks two ways: another decision whose supersedes: names this file, or a superseded_by: line on the file itself. Either one locks it.

The edit that creates the replacement is unaffected, and so is an edit that adds superseded_by: to the old file, because the marker is not on disk yet when the guard runs. That is the same idiom the plan lock uses: the transition is allowed, everything after it is not.

How the guard sees a change before it happens

A rule about the state a file is about to have cannot be checked against the file on disk. So the guard reconstructs the outcome first: edit-preview.mjs replays the proposed edit in memory — a whole-file write is the new content, a targeted edit is the substitution applied to the current file — and parses the settings block of the result. resolution.mjs then judges that block.

When an edit cannot be replayed, because the payload came from a tool whose shape we do not recognize, the preview falls back to scanning the payload for a settings-block-shaped state: line and merging the known keys it finds over the block on disk. The fallback reads lines out of context and is honest about it in its comments; the exact path covers the write and edit shapes Claude sends.

Why it is shaped this way

The knowledge directories existed long before anything asked for them, and they stayed empty. A rule nobody is ever stopped by is a suggestion. Putting the demand at the resolution edit means the cost of documenting lands on the person who just did the work and still has it in their head, which is the only time the document is cheap to write and accurate.
