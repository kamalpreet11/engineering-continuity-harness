knowledge-gate — make the knowledge base mandatory

Refuse to mark a plan implemented until it accounts for the concepts, decisions, and specs it produced, and enforce the resolution fields the rules already promise.

implemented knowledge concepts decisions specs gate resolution lock frontmatter
Created 2026-07-25 · Implemented 2026-07-25

Context

The harness creates docs/concepts/, docs/decisions/, and docs/specs/ at install time, ships a template for each, and renders them on the hub page. Nothing ever asks for them. No hook, no rule, and no instruction says when one is owed, so in practice they stay empty — including in this repo, after five shipped plans.

Those directories exist so the knowledge base grows as the software gets built. Optional means never. This plan puts the demand at the one moment every piece of work must pass through: the flip to state: implemented.

Two rules the documents already promise but nothing checks get closed by the same code. RULES.md says an abandoned plan must record a reason and a superseded plan must link its replacement. knowledge.md says a decision locks the moment a newer decision replaces it, when in fact only plan files lock.

Approach

A hook sees a file path and a proposed edit. It cannot read the session, so it can never decide on its own that the work invented a new concept. The enforcement therefore splits in two.

The instructions carry the judgement: knowledge.md defines when something counts as a concept, a decision, or a spec, and RULES.md — injected into every session — carries the rule itself. The hook carries the refusal: when a plan flips to a resolved state, its settings block must account for its knowledge with paths that exist on disk. The hook never judges whether a document is any good, only that the plan accounted for it. It is a forcing function, not a reviewer.

Frontmatter contract

Two new plan fields, checked only when a plan flips to implemented:

knowledge: concepts/auth-flow.html | decisions/token-storage.html

Pipe-separated, the same style as keywords. Paths are relative to docs/; a leading docs/ is tolerated. Every entry must sit under concepts/, decisions/, or specs/, and must exist.

knowledge: none
knowledge_reason: dependency version bump only, no behavior or pattern changed

none is the escape hatch and requires a reason in plain English, the same way an abandoned plan requires one. Skipping stays possible; it never becomes silent.

Abandoned and superseded plans shipped nothing into the project, so they owe the knowledge base nothing.

Resolution fields

Every flip out of created must carry its companion fields:

Resulting stateRequired
implementedimplemented: date, plus the knowledge accounting above
abandonedabandoned: date and abandoned_reason:
supersededsuperseded: date and superseded_by:

Decision lock

A decision file becomes read-only once a newer decision replaces it. Because knowledge.md says the old file stays exactly as it was, the lock reads two signals: another file in docs/decisions/ carrying supersedes: that names this one, or a superseded_by: line on the file itself. The edit that writes the replacement is unaffected, and the edit that adds superseded_by: to the old file still passes, because the marker is not on disk when the check runs. That is the same idiom the plan lock already uses.

Where the code goes

guards.mjs stays the dispatcher it is today. The new logic lands in two small modules beside it: edit-preview.mjs works out what a file will contain after a proposed edit, and resolution.mjs holds the rules as a pure function over two settings blocks. payload.mjs gains pickEdit so all four agents hand the guard the same shape. Where an edit cannot be simulated exactly — an unfamiliar payload, or a patch format — the guard falls back to scanning the payload for a settings-block-shaped state: line and merging what it finds over the file on disk.

Verification

A driver outside the repo pipes crafted payloads into .harness/bin/hooks/claude/guard.mjs, the real entry point, and asserts each decision: a flip with no knowledge: is refused; none without a reason is refused; none with a reason passes; a missing or misplaced path is refused and named; a real path passes; each resolution missing its date or reason is refused; an ordinary edit to a live plan passes; a replaced decision is read-only while an unreplaced one is not; and a whole-file write reaches the same verdict as the equivalent fragment edit.

The four existing rules must be untouched: no code edit without an active plan, no writing the generated indexes, no editing a resolved plan, no commit on main.

Then the real test. This plan is the first thing the new gate judges: resolving it before its documents exist must fail, and succeed once they do.

Knowledge

This work produced two documents, both named in this plan's knowledge: field.

  • concepts/document-lifecycle.html — how a plan and a decision reach their final state, and what the harness demands at that moment.
  • decisions/knowledge-accounting.html — accounting is a declaration of paths that must exist, not proof from a branch diff.

No spec: the work followed the shape the engine already had, pure rule modules behind per-tool adapters, rather than establishing a new pattern.
